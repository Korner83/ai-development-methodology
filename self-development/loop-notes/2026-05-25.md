## What didn't work — Run 2 operational issue

**Agent role + write permission interaction.** First Run-2 attempt spawned the Opus cold-read agent in the `Explore` role. Explore is read-only (no Edit/Write tools). The agent completed the cold-read correctly and returned ~43 findings as text, but couldn't apply them to the file. Lost ~5 minutes plus the cost of one Opus agent run when the orchestrating session had to re-spawn in `general-purpose` role.

**Root cause:** [`AUTONOMOUS_LOOP.md "fresh session" definition](../AUTONOMOUS_LOOP.md#operational-definition-of-fresh-session) requires "no prior turns referencing this project" and "ideally a different model family," but says nothing about agent role / tool availability. The loop's prompt step 6 ("CROSS-AI VALIDATION") implies fresh = read-only because cross-AI validation is non-destructive, but **cold-reads need write permission to land findings.** Cross-AI validation and cold-reads are not the same operation, but both use "fresh session" language.

**Suggested methodology addition** (surface for maintainer; not auto-applied per Constraint 1):

> Add a sentence to `AUTONOMOUS_LOOP.md` "Operational definition of fresh session" or to `methodology/10_testing_and_verification.md "Cross-AI validation"`:
>
> _"Fresh-session agents that must land output in a file (e.g., cold-read findings, classification tables) need a role with Write/Edit tools — use `general-purpose` or a project's equivalent, not a read-only role like `Explore`. Read-only roles are correct for verification (cross-AI Done-means checks) but wrong for production work."_

This is a one-sentence clarification, not a methodology rewrite. Ship in the next patch release or fold into BL-0009/0010's classification + summary work.

## Run 3 — methodology-change suggestions surfaced

29 findings + 4 cross-batch from Run 3. The two new v1.13.0 sub-sections (in 09 + 10) had real gaps — a useful signal that the same-release cold-read does catch its own additions. Highlights for BL-0009's two-axis classification:

**New v1.13.0 sub-section gaps (likely T1, surgical):**

- **`methodology/09_git_workflow.md` patch-branch convention — area-prefix policy unspecified.** The convention says `<area>-patch/YYYY-MM-DD-NN` with examples (`methodology-patch`, `designsystem-patch`, `spec-patch`) but doesn't say how a project picks or documents its area prefixes. New adopter has no guidance on whether `methodology-patch` is canonical for this project or whether they're free to pick their own. Recommend a single sentence: "Each project records its area prefixes in `09_git_workflow.md` or equivalent project doc."
- **`methodology/09_git_workflow.md` — "never auto-merge" wording.** Tier matrix says "loop never auto-merges a patch branch." But the affirmative table at lines ~250-290 (the can/can't list for AI agents in git) uses ⚠ for "Creates release tags only with explicit user OK" and "Opens GitHub Releases only with explicit user OK" — the same ⚠ that could plausibly read as "with permission, OK." Cold reader could mistake patch-branch merging as ⚠ rather than ✗. Recommend explicit ✗ row: "Merges a patch branch into the trunk — always maintainer-led, even when cross-AI PASS on diff-verification."
- **`methodology/10_testing_and_verification.md` two-modes — ambiguous PASS/FAIL for partial diff-verifications.** What happens when grounded=PASS, correct=PASS, scoped=CONCERN (e.g., diff touches the right region but also adds a stray whitespace change)? The doc doesn't say. Recommend: "A PASS on all three axes is required; any FAIL or CONCERN blocks the patch branch from being offered for merge until resolved."
- **`methodology/10_testing_and_verification.md` two-modes — "Done-means" term collision.** The two-modes section uses "Done means" loosely; the BL item template uses "Done means" as a load-bearing section header. Subtle but a cold reader could collapse the two. Recommend: rename the loose usage to "the validator confirms" or similar.

**Cross-batch findings (00–05 vs 06–11) — likely T1, surgical except where noted:**

- **Em-dash vs hyphen-minus drift in `Lock: —` field.** The DoD checklist in `07_definition_of_done.md:410` uses ASCII hyphen `Lock: -` while every other location uses em-dash `Lock: —`. Copy-paste from the checklist produces non-matching items. **T0 candidate** — pure cosmetic fix in one location.
- **"2+ occurrences" promotion trigger.** Doc 08 (`08_lessons_and_memory.md`) says lessons promote to durable rules when seen twice; doc 04 (`04_backlog_items.md`) doesn't reference this in the item-pattern discussion where reused lessons would actually be invoked. Cross-link or briefly restate.
- **Authority chain ordering inconsistency.** Doc 00's Authority section and doc 06/07's Authority sections don't enumerate the layers in the same order. Cold reader can't tell which is canonical. T1.
- **Lock-override rule omitted from hard-rules tables.** Doc 05 says "AI agents never override locks." But the hard-rules table in `00_README.md` and the can/can't table in `09_git_workflow.md` and the human-roles ownership table in `11_human_roles.md` all omit this. The rule is in one doc; three other docs that summarize "the inviolable rules" don't surface it. T1 — add a row to each table.

**Cold-read pattern observations (potentially methodology-level):**

- **Zero stale findings in Run 3.** Run 2 had 3 stale findings (the grep regression among them); Run 3 had 0. The methodology's actual content holds up — drift is happening at the *clarity* and *consistency* axes, not at the *correctness* axis. Worth telling adopters: "If your six-month eval surfaces zero stale findings, the methodology is healthy. If it surfaces many stale findings, the methodology has drifted from practice and needs surgery." Useful as a calibration sentence for adopters running their own eval cycles.

## Run 4 — what worked

- **Escalate-on-doubt actually caught over-claims.** The Sonnet tier-verifier sampled 10 T0/T1 findings and flagged 5 as T1 → T2 (F07 numbering convention, F13 parked→done state machine, F14 solo:1 default, F21 status-flip rule wording, F40 patch-branch ✗ row). All 5 were borderline cases the Opus classifier called T1 — and all 5 implied policy decisions or rule changes the maintainer should own. Without the verifier, those would have shipped in v1.14.0 without proper deliberation. **The matrix is not theatre.**
- **Diff-verification caught real correctness bugs.** The post-patch Sonnet diff-verifier found: 1 broken cross-doc anchor (`#item-skeleton` vs actual `#item-heading--frontmatter-table-skeleton`), 1 inaccurate inline paraphrase (`XS = under one focused session` vs canonical `XS = under 2 hours`), 1 typo (`greppping`). All three were mechanical mistakes Opus introduced but didn't notice when authoring 30 patches. The diff-verification gate has now demonstrated it catches what the implementing agent misses.
- **The two-axis classification scaled.** ~60 findings classified in one Opus pass with the per-finding ID structure (F01–F59) gave the verifier and the maintainer a stable reference vocabulary. The classification table in the eval file is the canonical artifact other agents (and future maintainers) read.
- **30 patches in one batch was manageable.** Single patch branch (`methodology-patch/2026-05-25-01`) + single diff-verification pass + single commit per logical chunk worked at this volume. For a much larger batch (100+ patches across more files), the pattern would benefit from per-doc branches or sub-batches to keep verifier scope tractable.

## Run 4 — what to refine before next cycle

- **The Opus classifier was over-confident.** 5 escalations on a 10-finding sample = 50% over-claim rate. Two routes to reduce: (1) bake more specific T1-vs-T2 examples into the classification prompt so Opus self-rejects borderline calls; (2) make the verifier sample size scale with batch size rather than fixed at 10. For 60 findings, sampling 10 may miss issues in the 36 ship-now patches. Next cycle: 1-in-3 sampling minimum.
- **The Tier-A grep-fix demo in v1.13.0 was a pre-flight.** v1.14.0 demonstrates the cycle at production volume. The pre-flight vs production gap surfaced one ergonomic improvement: when the implementing agent makes inline paraphrases of content from another doc (e.g., paraphrasing doc 04's effort definitions in doc 11), the agent should *quote* rather than *paraphrase* to avoid drift. Worth folding into the next AUTONOMOUS_LOOP.md revision.
- **CHANGELOG updates pile up.** Each loop run added an [Unreleased] entry; by Run 4 there were 4 stacked entries. The v1.14.0 release rolled them into the release narrative, which works but felt awkward. Possible improvement: per-run CHANGELOG entries should land *under the upcoming release header* rather than [Unreleased], so the release prep doesn't need to re-organize.
